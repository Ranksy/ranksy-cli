# Ranksy CLI — Design Spec

**Date:** 2026-08-28
**Status:** Approved for implementation planning
**Owner:** Goran

## Summary

A command-line tool, `ranksy`, that lets Ranksy customers run automations
against the Ranksy API from the terminal and CI, as an alternative to the MCP
server. It is a **scriptable toolkit**: each command maps to an API operation,
but with the quality-of-life features that make real pipelines pleasant — JSON
or table output, polling with `--watch`, config profiles, and CI-friendly exit
codes. It is stateless; there is no local workflow engine.

The tool is written in Rust and distributed as prebuilt static binaries.

## Goals

- Give customers a scriptable surface over the Ranksy API that fits bash, cron,
  and CI, not just agent/MCP usage.
- Reuse the existing API v1 keys and issuance flow with no backend changes.
- Keep the typed API client in sync with the API automatically via the existing
  `openapi.json` export, so the CLI does not drift as endpoints change.
- Ship a clean, curated command surface — not a raw, generated dump of every
  endpoint.

## Non-goals

- No workflow runtime, scheduler, or local state (explicitly deferred; the CLI
  stays stateless).
- No new backend auth work. The CLI uses the same customer API keys already
  issued for API v1.
- No Homebrew, cargo/crates.io, or npm distribution at launch (the architecture
  keeps these as cheap later additions, but they are out of scope for v1).
- No embedded/local MCP host.

## Users

Ranksy customers — Shopify app developers tracking ASO, rankings, keywords,
reviews, and installs. Comfortable in a terminal and CI. Many are JS/Shopify
developers, which informs a possible later npm channel but not v1.

## Architecture

### Repository

A new standalone repository, `ranksy-cli`, separate from the Laravel
application. It is a Cargo workspace with two crates so the generated API client
is cleanly isolated from the command layer:

```
ranksy-cli/
  Cargo.toml            # workspace
  openapi.json          # vendored, synced from the app's Scramble export
  crates/
    ranksy-api/         # generated typed client + auth/config wrapper (library)
    ranksy-cli/         # clap commands, output, config -> binary `ranksy`
  install.sh            # generated by cargo-dist
  dist-workspace / dist config
  .github/workflows/    # release pipeline (generated by cargo-dist)
  docs/
```

Boundary contract:

- `ranksy-api` knows the API wire format and auth. It knows nothing about the
  CLI, argument parsing, or terminal output. Consumers use its typed methods.
- `ranksy-cli` knows UX — parsing, config resolution, output rendering, exit
  codes. It knows nothing about HTTP wire details. It depends only on the public
  interface of `ranksy-api`.

Each crate is independently testable.

### Client layer (`ranksy-api`)

- The typed client is generated from `openapi.json` using **`progenitor`** (the
  Oxide OpenAPI-to-Rust generator, which emits an async `reqwest`-based client).
  Chosen over `openapi-generator` (Java toolchain, less idiomatic output). The
  generated types track the API, giving us the "no drift" property that is the
  point of the hybrid approach.
- Generation runs at build time from the vendored `openapi.json`. Regenerating
  after an API change is a matter of re-syncing `openapi.json` and rebuilding.
- A thin hand-written wrapper around the generated client:
  - Injects the customer API key. The CLI uses the **same API key customers
    already issue for API v1, sent in the same header/parameter that API v1
    already accepts.** The exact header is read from `openapi.json` / the
    existing API docs during implementation (assumed `Authorization: Bearer
    <key>` unless the export shows otherwise). See Assumptions.
  - Sets the base URL, default `https://ranksyapp.com/api`, overridable via flag
    or env for staging.
  - Adds retry with backoff on `429` and `5xx` responses, since the API sits
    behind rate limits and pgbouncer. Retries are bounded and only applied to
    idempotent reads by default.
- Async runtime: `tokio`, because `progenitor` emits an async client. The cost
  over blocking `reqwest` is minimal for a CLI.

### Command layer (`ranksy-cli`)

- `clap` v4 with the derive API. Commands follow a noun-verb structure and are
  curated to the automation-relevant slice of the API (not every endpoint):

  ```
  ranksy login <key>
  ranksy whoami
  ranksy apps list
  ranksy rankings get --app <id> --keyword <kw> [...]
  ranksy keywords list | track | untrack
  ranksy reviews list
  ranksy installs get
  ranksy listing get | improve
  ```

  The exact command set is finalized against `openapi.json` during
  implementation; the list above is the intended shape, not a frozen contract.

- Global flags:
  - `--json` — emit raw JSON instead of a table.
  - `--api-key <key>` — override the resolved key.
  - `--base-url <url>` — override the API base URL.
  - `--app <id>` — default app, falls back to config.
  - `--watch <secs>` — re-run the command on an interval (the polling
    ergonomic).
  - `-q / --quiet` — suppress non-essential output.

- Each command calls a typed method on `ranksy-api`, then renders the result
  through the output layer.

### Auth and config

- Key resolution precedence, highest first:
  1. `--api-key` flag
  2. `RANKSY_API_KEY` environment variable
  3. `~/.config/ranksy/config.toml`
- `ranksy login <key>` writes the key to the config file with `0600`
  permissions. Config paths resolved via the `directories` crate.
- The env-var path is the clean, file-free route for CI.
- `config.toml` may also hold a default `app` id and `base_url`.

### Output and exit codes

- Default output is a human-readable table via `tabled`.
- `--json` emits the raw JSON response, suitable for piping to `jq`.
- Color respects `NO_COLOR`; output auto-degrades to plain when stdout is not a
  TTY.
- Exit codes:
  - `0` — success
  - `2` — usage / argument error (clap default)
  - non-zero (distinct from `2`) — API or runtime failure, so CI can gate on it
- Error handling: `anyhow` in the binary crate for ergonomic top-level errors;
  `thiserror` in `ranksy-api` for typed library errors.

### Distribution and CI

- **`cargo-dist`** generates the release pipeline: it builds static binaries and
  produces GitHub Releases with a `curl | sh` installer and checksums.
- Launch targets:
  - Linux `x86_64` and `aarch64`, statically linked via musl.
  - macOS `x86_64` and `aarch64`.
  - Windows `x86_64` (msvc).
- Launch install channel: the `curl | sh` script plus GitHub Releases only.
  Homebrew, crates.io, and npm are deliberately not wired up, but `cargo-dist`
  makes each a small later addition.
- Chosen over a hand-written `release.yml` for less maintenance and a
  ready-made, checksummed installer.

### Testing

- Unit tests: argument parsing, config resolution precedence, output rendering.
- Integration tests: `wiremock` stands in for the API. Tests assert the outgoing
  request shape (auth header, path, query parameters) and the rendered output.
- Golden tests: fixed fixtures for both table and JSON rendering.
- No test touches the live API.

## Data flow

1. User runs `ranksy <command> [flags]`.
2. `ranksy-cli` parses args and resolves the API key and base URL by precedence.
3. It constructs the `ranksy-api` client wrapper with those settings.
4. It calls the typed method matching the command; the wrapper injects auth and
   applies retry/backoff.
5. The typed response returns to the command layer, which renders it as a table
   or raw JSON and sets the process exit code.

## Backend dependency

None for auth — the CLI reuses the existing API v1 keys and issuance flow with
no changes. The only ongoing dependency is the `openapi.json` export already
produced by Scramble, which is vendored into the repo and re-synced when the API
changes.

## Assumptions

- API v1 accepts the customer key as a bearer token in the `Authorization`
  header. This is confirmed against `openapi.json` / the API docs at the start
  of implementation; if the real mechanism differs (e.g. a custom header or
  query parameter), only the thin auth wrapper in `ranksy-api` changes.
- `openapi.json` is complete and accurate enough for `progenitor` to generate a
  usable client. If specific operations are missing or malformed in the export,
  those get patched in the vendored copy or hand-authored in the wrapper, and
  the gap is reported back for the API-side export to be fixed.

## Open items resolved during brainstorming

- CLI role: scriptable toolkit (stateless, ergonomic).
- Auth: API key, same as API v1, no backend changes.
- Command mapping: hybrid — generated typed client, curated command layer.
- Distribution at launch: `curl | sh` + GitHub Releases only.
- Generator: `progenitor`. Release tooling: `cargo-dist`. Runtime: async
  `tokio`.

## Future extensions (out of scope, noted for design safety)

- Additional install channels (Homebrew, npm, crates.io).
- A workflow-runtime mode running declarative files.
- Shell completions and man pages (both are cheap `clap`/`cargo-dist` addons).
